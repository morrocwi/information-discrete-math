# IDM Symbolic Kernel v2 — Pillar: Exact/Certified Numeric Types + Coercion

Phase 1 architecture spec. Design-only — no implementation. Grounded in the actual current
files `idm/exact.py`, `idm/interval.py`, `idm/certified.py`, `idm/symbolic.py`, `idm/functions.py`,
`idm/analysis.py`, `idm/solve.py`, `tools/certified_readout.py`.

Tier vocabulary used throughout (unchanged from the existing `solve.py` discipline):
`Th_coqc` (named Coq theorem governs the result) → `exact` (finite, decidable, no float, unproven)
→ `finite_diagnostic` (numeric to a declared tolerance) → `+ℝ-Open`/`Dr` (declared open/deferred,
never silently answered) → `HOLD` (refuses to emit a number; the honest non-answer). `CERTIFIED` /
`HOLD` is the *status* vocabulary from `certified.Readout`; tier is a separate axis attached by
`solve.py`. This pillar does not invent a third vocabulary — see §(e).

---

## (a) Data structures

The tower is a **strict coercion ladder**, not a class hierarchy with implicit widening. Every type
below is a `dataclass` (or `NamedTuple`-equivalent — dataclass chosen for readability of the spec;
`slots=True` recommended for the leaf numeric types given the current `Readout.__slots__` precedent).
No type auto-widens to the next; every step across a rung is an explicit, named coercion function
(§b) that itself returns a tier-tagged result, never a bare value.

```python
from __future__ import annotations
from dataclasses import dataclass, field
from fractions import Fraction as Q
from enum import Enum
from typing import Optional, Callable, Union

# ---- tier / status vocabulary (imports from idm.certified, not redefined) ----
from .certified import CERTIFIED, HOLD          # "CERTIFIED" / "HOLD" — existing string constants
Tier = str                                       # "Th_coqc" | "exact" | "finite_diagnostic" | "+R-Open" | "Dr"


# ---- rung 0: exact integer ----
@dataclass(frozen=True, slots=True)
class ExactInteger:
    value: int                       # arbitrary-precision Python int — already how exact.py works
    # no separate 'tier' field: an ExactInteger IS tier "exact" by construction (type-level guarantee)


# ---- rung 1: exact rational ----
@dataclass(frozen=True, slots=True)
class ExactRational:
    value: Q                         # fractions.Fraction — already the repo's Q alias
    # Coercion FROM ExactInteger is total and lossless (ℤ ⊂ ℚ); coercion TO ExactInteger is partial
    # (only when value.denominator == 1) and must go through coerce_down() (§b), never silent.


# ---- rung 2: algebraic number ----
@dataclass(frozen=True, slots=True)
class AlgebraicNumber:
    min_poly: tuple[Q, ...]          # minimal/annihilating polynomial, coeffs low→high (exact.py convention)
    interval: "RealBall | ComplexBall"   # an ISOLATING enclosure that contains exactly ONE root of min_poly
    index: int                       # which root of min_poly this is, for re-isolation after precision escalation
    is_rational: bool = False        # True short-circuits to the ExactRational fast path (degree-1 min_poly)
    # An AlgebraicNumber is exact in identity (defined by min_poly) but only ENCLOSED numerically —
    # this is why it carries a ball, not a Fraction: irrational algebraics have no finite Q readout.


# ---- rung 3/4: certified enclosures (real / complex) ----
class Rounding(Enum):
    DOWN = "down"; UP = "up"; NEAREST = "nearest"   # directed-rounding discipline for interval arithmetic

@dataclass(frozen=True, slots=True)
class RealBall:
    lo: "mpmath.mpf"                 # rigorous lower bound, directed-rounding DOWN
    hi: "mpmath.mpf"                 # rigorous upper bound, directed-rounding UP
    prec_dps: int                    # decimal precision this ball was computed at (mp.mp.dps at creation)
    # Invariant: lo <= true_value <= hi is a PROVEN fact given the algorithm's stated hypotheses, not a
    # probabilistic/statistical claim. This IS idm/interval.py's {"lo":..,"hi":..,"certified":True} dict,
    # promoted to a first-class type. width = hi - lo; midpoint = (lo+hi)/2 are derived, not stored.

@dataclass(frozen=True, slots=True)
class ComplexBall:
    re: RealBall
    im: RealBall
    prec_dps: int
    # A rectangular (box) enclosure, consistent with mpmath.iv's real-axis-only rigor; a disc enclosure
    # is NOT introduced in Phase 1 (see out-of-scope §g) — box composes trivially with RealBall ops.


# ---- rung 5: symbolic expression (the ALREADY-EXISTING tree in idm/symbolic.py, adopted not replaced) ----
# idm/symbolic.py's tree (Fraction | ('var',name) | ('add',[..]) | ('mul',[..]) | ('pow',b,e) |
# ('func',name,arg)) IS SymbolicExpression for Phase 1. We do NOT reimplement it as a dataclass tree —
# see (d) migration. A typed wrapper is added ONLY for the domain/assumption tag that is currently
# absent (ground map §4):
@dataclass(frozen=True)
class SymbolicExpression:
    node: tuple | Q                  # the existing idm.symbolic tree, unchanged shape
    domain: Optional["DomainTag"] = None   # None = "no restriction declared" (today's implicit behavior)

@dataclass(frozen=True)
class DomainTag:
    """The minimal domain/assumption object the ground map (§4) found completely absent. Phase 1 scope
    is limited to what (x^a)^b, log(ab), sqrt(x^2) rewriting actually needs — see (e)."""
    var: str
    predicate: str                   # one of: "positive", "nonzero", "real", "integer", "unrestricted"
    # deliberately a closed enum-like string set, not an open constraint solver (out of scope, §g)


# ---- rung 6/7: polynomial / matrix over a declared domain ----
class Domain(Enum):
    Z = "Z"; Q = "Q"; ALGEBRAIC = "algebraic"; REAL_BALL = "real_ball"; COMPLEX_BALL = "complex_ball"

@dataclass(frozen=True)
class Polynomial:
    coeffs: tuple                    # low→high, exactly exact.py's convention (poly_add/poly_mul/…)
    domain: Domain                   # declares what TYPE the coeffs are drawn from — never mixed silently

@dataclass(frozen=True)
class Matrix:
    rows: tuple[tuple, ...]
    domain: Domain
    # exact.py's matrix functions (mat_mul, determinant, rref, …) already operate structurally this
    # way (plain nested lists of Fraction) — Matrix is a thin typed wrapper, not a reimplementation.


# ---- the verdict wrapper every public op returns (unifies certified.Readout + interval.py's dict idiom) ----
@dataclass(frozen=True)
class Certificate:
    value: Optional[Union[ExactInteger, ExactRational, AlgebraicNumber, RealBall, ComplexBall,
                           SymbolicExpression, Polynomial, Matrix]]
    status: str                      # CERTIFIED | HOLD  (reuse idm.certified's two constants verbatim)
    tier: Tier                       # Th_coqc | exact | finite_diagnostic | +R-Open | Dr
    bound: Optional["mpmath.mpf"] = None      # proven |value - target| <= bound, when applicable
    reason: Optional[str] = None              # populated on HOLD, and on CERTIFIED for provenance
    coq_theorem: Optional[str] = None         # mirrors solve.py's _COQ_BACKED attachment convention
```

Design notes on the tower:

- **No implicit `__float__`/`__int__` widening anywhere.** Python's normal numeric-tower duck typing
  (`int` → `float` on mixed arithmetic) is exactly the failure mode this pillar exists to prevent —
  every rung transition is a named function call in §(b), so "silently turns exact into float" is
  structurally impossible: there is no `__add__` between `ExactRational` and `RealBall` that returns
  a bare float; there is only `coerce_up(ExactRational, target=RealBall, prec_dps=N) -> Certificate`.
- `AlgebraicNumber` deliberately does NOT store a `Fraction` approximation anywhere — its only numeric
  content is the enclosing ball, re-isolated on demand. This matches the ground-map finding that
  `rational_roots` (exact.py) and `poly_roots`/Durand–Kerner (analysis.py) are currently two
  *disconnected* mechanisms (one exact, one iterative-numeric) with no shared "this is provably a
  root of this polynomial" object between them — `AlgebraicNumber` is exactly that missing object.
- `Certificate` is deliberately NOT a new third status vocabulary. It reuses `CERTIFIED`/`HOLD` from
  `idm/certified.py` verbatim and the tier strings `solve.py` already assigns. See (e).

## (b) Public interface contract

Signatures other pillars (the future `SymbolicExpression`-consuming diff/simplify pillar, the
optimization/root-finding pillars, and the ~258 `solve.py` kind-handlers) call. Every function
returns a `Certificate`, never a bare value — this is the one non-negotiable contract of the pillar.

```python
# ---- construction (parse/lift a raw Python value into the tower, at the LOWEST rung that fits) ----
def from_int(n: int) -> Certificate: ...
def from_str_rational(s: str) -> Certificate: ...        # "3/7" -> ExactRational; never guesses a float
def from_fraction(q: Fraction) -> Certificate: ...        # lifts the repo's existing Q values, tier="exact"

# ---- coercion: the ONE mechanism that ever crosses a rung, always explicit and always tier-tracked ----
def coerce_up(x: <tower type>, target_rung: type, *, prec_dps: int = 30) -> Certificate:
    """Widen towards the continuum end (Z->Q->Algebraic->RealBall->ComplexBall). NEVER silent, NEVER
    automatic — caller always names target_rung and (for ball targets) the precision. Tier of the
    result is downgraded honestly: Z/Q/Algebraic-exact inputs coerced to a Ball come back tier
    'finite_diagnostic' or 'Th_coqc'-if-the-enclosure-algorithm-is-proven, NEVER 'exact' — the enclosure
    is finite-precision even though the source was exact. This is the single choke point that makes
    'never silently turns exact into float' enforceable: grep the codebase for coerce_up call sites
    to audit every place precision is knowingly given up."""

def coerce_down(x: <tower type>, target_rung: type) -> Certificate:
    """Narrow towards ℤ (RealBall->AlgebraicNumber->ExactRational->ExactInteger), PARTIAL — returns
    HOLD (tier 'exact', status HOLD, reason 'not exactly representable at target rung') when the
    narrowing isn't exact, e.g. coerce_down(RealBall(...), ExactRational) when the ball's width hasn't
    collapsed to a single rational. This is where 'certified.Readout'-style honesty pays for itself:
    a ball that LOOKS like it converged to a nice rational is only asserted exact when lo==hi as
    Fractions after an exact-arithmetic ball (see certified_root's own "reject unless proven" pattern
    in idm/interval.py:66-78, generalized here)."""

# ---- ball arithmetic: directed-rounding interval ops (rehosts idm/interval.py's ieval engine) ----
def ball_add(a: RealBall, b: RealBall) -> RealBall: ...
def ball_mul(a: RealBall, b: RealBall) -> RealBall: ...
def ball_div(a: RealBall, b: RealBall) -> Certificate: ...   # HOLD if 0 in b's enclosure (division by
                                                               # a ball that may contain zero is unsafe)
def ball_apply(fn_name: str, arg: RealBall) -> Certificate:
    """Interval-safe application of one of interval.py's _NS functions (exp/sin/cos/log/sqrt/tan).
    HOLD when the enclosure would cross a singularity (log/sqrt of a ball containing <=0, tan of a
    ball containing an odd multiple of pi/2) — mirrors certified_root's own singularity check."""

def escalate_precision(x: RealBall | ComplexBall, target_width: "mpmath.mpf") -> Certificate:
    """AUTOMATIC precision escalation: re-run the ball's generating computation at higher mp.dps until
    hi-lo <= target_width or a declared max_dps ceiling is hit (default ceiling: caller-supplied, no
    silent infinite loop — mirrors certified_root's `it=400` bounded-iteration discipline). Returns
    HOLD with reason 'precision ceiling reached without convergence' rather than looping forever or
    silently returning a wide ball as if it were narrow."""

def condition_number(expr: SymbolicExpression, env: dict[str, RealBall]) -> Certificate:
    """A CERTIFIED (not estimated) bound on |df| ~ |f'(x)| * |dx| via ball-arithmetic evaluation of
    the ALREADY-DIFFERENTIATED tree (idm.symbolic.diff, unchanged) at the input ball — i.e. condition
    number is itself an enclosure, not a float heuristic. Feeds escalate_precision's stopping decision:
    'is this instability or genuine cancellation' is answered by comparing the condition-bound-implied
    width against the observed ball width, not by guessing."""

# ---- exact arithmetic passthroughs (rehost exact.py — see (d); signatures UNCHANGED, only re-typed) ----
def exact_add(a: ExactRational, b: ExactRational) -> ExactRational: ...   # wraps exact.py arithmetic
                                                                            # (Fraction + is already exact;
                                                                            # no new algorithm needed)
def exact_determinant(A: Matrix) -> Certificate: ...          # wraps exact.determinant, tier="exact"
def exact_solve_linear(A: Matrix, b: tuple) -> Certificate: ...  # wraps exact.solve_linear

# ---- symbolic bridge: what solve.py's kind-handlers actually call ----
def to_callable(expr: SymbolicExpression, prec: type) -> Callable:
    """Compiles a SymbolicExpression to a callable over ExactRational, RealBall, or ComplexBall —
    THE seam that closes the ground-map's finding #6.2: the numeric side (functions.py/interval.py)
    currently re-`eval()`s the raw string three times independently (functions.py's math_namespace,
    interval.py's _NS/ieval, solve.py's _CNS/_cfn). Phase 1 leaves those three eval() sites ALONE
    (see (d) — full rehosting of the numeric evaluators is Phase 2) and instead gives them ONE new
    shared option to call into instead of re-parsing the string, without breaking existing callers."""

def evaluate_exact(expr: SymbolicExpression, env: dict[str, ExactRational]) -> Certificate:
    """Exact evaluation when every leaf is rational and no func node with an irrational value (pi, e,
    non-rational trig/exp/log argument) is reached — else HOLD 'expression requires enclosure, use
    evaluate_certified'. This is the honest replacement for symbolic.py's evaluate() (idm/symbolic.py:
    205-218), which SILENTLY drops to mp.mpf for every func node today — see (e) HOLD placement."""

def evaluate_certified(expr: SymbolicExpression, env: dict[str, RealBall], prec_dps: int = 30) -> Certificate:
    """Ball-arithmetic evaluation via ball_apply, with automatic escalate_precision retry once before
    surfacing HOLD. This is the certified-enclosure-tier successor to interval.py's ieval()."""
```

Complexity/behavioral contract each caller may rely on (see (c) for derivations):
`coerce_up`/`coerce_down` are O(1) to O(poly-size) depending on target rung; `ball_apply`/`ball_add`
are O(1) mpmath calls; `escalate_precision` is O(k) reruns bounded by a caller-supplied ceiling;
`condition_number` is one extra tree evaluation (same cost class as the value itself).

## (c) Key algorithms and complexity

1. **Exact rational arithmetic** (`ExactRational`, rehosting `exact.py`'s bare `Fraction` ops):
   GCD-reduced at every `+`/`*` by Python's `Fraction` internals — O(log(numerator)·log(denominator))
   per op via Euclidean GCD; no change to existing complexity, only a type wrapper.

2. **Ball arithmetic** (`RealBall`/`ComplexBall` ops): directed-rounding `mp.iv` primitives, O(1) per
   op at fixed precision `prec_dps`; `mpmath`'s cost per digit is the usual O(M(d)) for multiplication
   at `d`-digit precision (M = multiplication complexity, effectively near-linear for the precisions
   this repo uses, dps ∈ [30,50]). No new algorithm — `interval.py`'s existing `_ival`/`ieval`
   machinery, retyped.

3. **`certified_root`/`verified_range`-style bisection and subdivision** (already in `interval.py`,
   rehosted unchanged as the implementation *underneath* `evaluate_certified`'s escalation path):
   O(depth) subdivisions for `verified_range` (`idm/interval.py:36-47`, `depth=16` default → 2^16
   leaf boxes worst case, but pruned in practice), O(log(1/tol)) bisection steps for `certified_root`
   (`idm/interval.py:50-80`, `it=400` ceiling), O(boxes) priority-queue branch-and-bound for
   `certified_min` (`idm/interval.py:83-100`, `max_boxes=200000` ceiling) — all three algorithms are
   **unchanged**, only their entry point becomes `escalate_precision`/`ball_apply` calls instead of
   bare `ieval()` calls.

4. **Precision escalation** (new, `escalate_precision`): geometric doubling of `mp.mp.dps`
   (30→60→120→…) until `hi-lo <= target_width` or a caller ceiling is hit — O(log(target_prec /
   initial_prec)) reruns of the underlying ball computation, each rerun paying the O(M(d)) cost of
   (2) at the new precision. This is the "automatic precision escalation" the pillar's mandate names;
   it is new orchestration logic over existing primitives, not a new numeric algorithm.

5. **Algebraic root isolation** (`AlgebraicNumber` construction): rehosts `exact.py`'s
   `rational_roots` (rational-root theorem, O(divisors(a0)·divisors(an)) candidate trial, exact.py:171-193)
   as the degree-1-in-disguise fast path, and `analysis.py`'s `poly_roots` (Durand–Kerner,
   `analysis.py:126-148`, O(degree²) per iteration × `it=500` ceiling) for the general isolating-ball
   case — Durand–Kerner's complex roots become the `AlgebraicNumber.interval` `ComplexBall`, its
   iteration count becomes the tier evidence (`finite_diagnostic`, not `exact`, since Durand–Kerner
   convergence is not currently Coq-proven — matches the ground map's tier-honesty stance).

6. **Coercion cost**: `coerce_up`/`coerce_down` themselves are O(1) dispatch plus the cost of whatever
   rung-appropriate algorithm above they invoke; the NEW cost this pillar adds beyond what already
   exists is the audit/bookkeeping (tier stamping, HOLD-reason construction), which is O(1) per call.

No algorithm in this pillar is asymptotically novel — the design's contribution is making every
existing rehostable routine (interval.py's bisection/subdivision/branch-and-bound, exact.py's
Fraction/GCD/root-theorem code, analysis.py's Durand–Kerner) reachable through ONE typed, tier-honest
call surface instead of three duplicated `eval()`-based ones.

callers working (`idm/exact.py`, `idm/interval.py`, `idm/certified.py`, `idm/solve.py` all still

naming call left to whoever assigns the eventual module tree; referred to below as `idm/types.py`),

**The one behavioral change in Phase 1**: `symbolic.evaluate()` (`symbolic.py:205-218`) currently
does `if isinstance(e, Q): return mp.mpf(...)` and silently produces an `mp.mpf` for every symbolic
constant, including exact rational ones — this IS the "silently turns exact into float" pattern the
pillar's mandate explicitly forbids. `evaluate_exact`/`evaluate_certified` split this into two named,
tier-honest entry points: an all-rational expression stays `ExactRational` through `evaluate_exact`
(new capability — `symbolic.py` had no such path), and anything touching an irrational func node goes
through `evaluate_certified` and comes back a tier `finite_diagnostic` `RealBall`, never a bare
`mp.mpf`. The old `symbolic.evaluate()` function is left in place unchanged for existing callers
(none currently found calling it in `solve.py`'s registry — grep confirms `symbolic.py`'s `evaluate`
is not wired into any of the 258 kinds today, so this is a zero-blast-radius addition, not a breaking
change).

**`solve.py`'s registry mechanism (`_REG`, `kind()` decorator, `_norm`, `_ok`, `_readout`,
`_COQ_BACKED`, the tier-honesty pass at `solve.py:816-822`) is UNTOUCHED in Phase 1.** `Certificate`
objects convert to the existing `_ok`/`_readout` dict shape via a thin adapter
(`certificate_to_result(c: Certificate) -> dict`, added to `idm/types.py`, NOT a change to
`solve.py`'s own `_norm`/`_ok`/`_readout` bodies) so a handler can optionally build on the new tower
and still return exactly the dict shape `solve()` already expects. No 259th kind is added; no
existing kind's dict contract changes.

## (e) Alignment with readout-first tiers; where HOLD is returned

| Tower rung | Tier when constructed directly | Tier after `coerce_up` |
|---|---|---|
| `ExactInteger` | `exact` (finite, decidable, no float — by construction) | — |
| `ExactRational` | `exact` | — |
| `AlgebraicNumber` (rational-root fast path) | `exact` | — |
| `AlgebraicNumber` (Durand–Kerner isolation) | `finite_diagnostic` (iteration-bounded, not Coq-proven) | — |
| `RealBall`/`ComplexBall` | `finite_diagnostic` by default; `Th_coqc` ONLY for the two operations the repo already has Coq theorems for (`geom_series_certified`/`exp_certified`'s bound derivations, per `certified.py`'s docstring reference to `formal/IDM_Certified.v`) | when reached via `coerce_up` from an exact rung, tier is stamped `finite_diagnostic` (or `Th_coqc` if the specific enclosure algorithm used is in `_COQ_BACKED`-equivalent list) — **never silently inherits `exact` from the source** |
| `SymbolicExpression` | `exact` (tree is finite-rational by construction, matching `symbolic.py`'s own docstring claim) | — |

**HOLD is returned by this pillar at exactly these points** (each mirrors an existing HOLD pattern
already in the ground map, generalized to the new call surface rather than invented fresh):

1. `coerce_down` when the target rung cannot exactly represent the source (ball hasn't collapsed to
   a point rational) — generalizes `certified_root`'s "reject unless the bracket rigorously proves a
   root" discipline (`interval.py:66-78`) to the general narrowing case.
2. `ball_div`/`ball_apply` when the operation is undefined or singular on the enclosure (division by
   a zero-containing ball; `log`/`sqrt` of a non-positive-containing ball; `tan` at an odd multiple of
   π/2) — directly generalizes `certified_root`'s pole-rejection check.
3. `escalate_precision` when a caller-supplied precision ceiling is reached without the target width
   being achieved — generalizes the bounded-iteration discipline already present in `certified_root`
   (`it=400`) and `certified_min` (`max_boxes=200000`): **never loop unboundedly, never return a wide
   enclosure mislabeled as narrow.**
4. `evaluate_exact` when any leaf of the expression is not exactly rational-evaluable in the given
   environment (an irrational func-node value reached) — the caller is redirected to
   `evaluate_certified` rather than silently downgrading to float, closing the exact gap named in (d).
5. **Domain-unsafe symbolic rewrites** — per the mandate, `sqrt(x^2)→abs(x)`, `log(ab)`, `(x^a)^b`
   splitting are gated by `DomainTag`. Concretely: `(x^a)^b → x^(ab)` (today's UNCONDITIONAL collapse
   at `symbolic.py:117`, the ground map's named domain gap) becomes, under this pillar's `DomainTag`,
   `HOLD` (tier `exact`, reason `"(x^a)^b -> x^(ab) requires x>0 or integer exponents — no domain
   declared"`) whenever no `DomainTag(var=x_root, predicate="positive")`-or-equivalent is attached to
   the input `SymbolicExpression`; it proceeds only when the caller supplied one. This is Phase 1's
   concrete fix for the one live domain gap the ground map identified — **implemented as a HOLD gate
   at the coercion/kernel-object boundary, not as a change to `symbolic.simplify()`'s body itself**
   (that body-level change belongs to whichever pillar owns rewrite rules; this pillar only supplies
   the `DomainTag` type and the gate contract other pillars must check before calling the identity).
6. `AlgebraicNumber` construction when Durand–Kerker fails to converge within its iteration ceiling —
   generalizes `analysis.py:126-148`'s existing `it`/`tol` bounded-loop pattern.

**`Certificate.status`/`Certificate.tier` are two independent axes, matching the existing repo
convention** (`solve.py` already keeps `status` — ok/CERTIFIED/HOLD — separate from `tier` —
Th_coqc/exact/finite_diagnostic — and stamps both independently at `solve.py:816-822`). This pillar
does not collapse them into one, and does not introduce a fourth status string beyond the two
`idm/certified.py` already defines (`CERTIFIED`, `HOLD`) plus the plain-success `"ok"` string
`solve.py`'s `_ok()` already uses for non-`Readout` results.

## (f) Top 3 risks + mitigations

1. **Risk: coercion-point proliferation defeats the "never silent" guarantee in practice.** If every
   pillar/kind-handler is free to call `coerce_up`/`coerce_down` at will with ad hoc precision
   choices, the discipline degrades to "technically explicit, practically as arbitrary as before" —
   258 call sites each picking their own `prec_dps` is not meaningfully different from 258 call sites
   each `eval()`-ing a string into `mp.mpf`.
   **Mitigation**: Phase 1 ships `coerce_up`/`coerce_down` as the ONLY functions permitted to change
   rung — enforced by convention now (module boundary + docstring), and made auditable later by a
   grep-based CI check ("no `mp.mpf(`/`float(` call outside `idm/types.py`'s ball layer") — deferred
   to Phase 2 tooling, named here so it isn't lost. In Phase 1, the mitigation is architectural
   naming discipline plus this document being the reviewable contract, not yet an enforced lint.

2. **Risk: `AlgebraicNumber` re-isolation after precision escalation is not actually well-defined
   when two roots are close together** — Durand–Kerker roots can swap ordering/be ambiguous to
   disambiguate by index alone if two roots of `min_poly` fall inside overlapping balls at low
   precision (a real failure mode of numerical root isolation, not hypothetical).
   **Mitigation**: `AlgebraicNumber.index` is defined as "index into the SORTED-BY-BALL-CENTER root
   list at THIS PRECISION," and `escalate_precision` on an `AlgebraicNumber` must re-run root
   isolation from `min_poly` at the new precision and re-match by **disjointness**: if any two
   candidate balls still overlap at the target precision, `escalate_precision` returns `HOLD` with
   reason `"roots not yet separated — increase precision further or provide a bracketing interval"`
   rather than guessing which new-precision root corresponds to the old index. This is the same
   "prove it or HOLD" posture as `certified_root`'s pole check, applied to root disambiguation.

3. **Risk: `to_callable`/`evaluate_certified` becomes a fourth parallel evaluator instead of unifying
   the three that already exist** (`functions.py:math_namespace`, `interval.py:ieval`,
   `solve.py:_fn`/`_fn2`/`_seq`), because Phase 1 deliberately does NOT rewrite those three call sites
   (see (d), (g)) — so the codebase temporarily has FOUR string/tree evaluation paths, which is worse
   for maintainability than the three the ground map already flagged as a duplication problem.
   **Mitigation**: name this explicitly as accepted, temporary Phase 1 debt rather than hide it — the
   new evaluator is opt-in only for NEW kind-handlers built on the tower and for the domain-gated
   rewrite in (e)#5; Phase 2's job (named in (g)) is specifically to retire the three old `eval()`
   sites in favor of `to_callable`, not to have Phase 1 attempt that migration under this pillar's
   already-large scope.

## (g) Explicitly OUT of scope for Phase 1

- **Rewriting/retiring the three existing string-`eval()` evaluators** (`functions.py:57-69`,
  `interval.py:21-25`, `solve.py:55-61`) — Phase 1 adds `to_callable` as a new option, does not
  migrate existing call sites onto it. (Named as risk 3 above; explicit Phase 2 item.)
- **`ComplexBall` as a disc/annulus enclosure** — Phase 1 ships rectangular (box: `RealBall`×`RealBall`)
  complex enclosures only, matching what `mpmath.iv` already gives on the real axis; a proper complex
  disc arithmetic (tighter, avoids the "wrapping effect" of repeated box multiplication) is a known
  follow-on, not attempted here.
- **A general constraint/assumption SOLVER for `DomainTag`** — Phase 1's `DomainTag` is a closed,
  small predicate vocabulary (`positive`/`nonzero`/`real`/`integer`/`unrestricted`) attached by the
  caller, checked by simple equality/membership. It is NOT a general theorem-prover or SMT-backed
  assumption system — any such inference is out of scope; domain tags are declared, never inferred.
- **`Piecewise` result type.** Phase 1's `Certificate`/`DomainTag` machinery only implements the
  `HOLD` half of the mandate's "HOLD or Piecewise" choice for domain-ambiguous rewrites. A
  `Piecewise` value type is a natural Phase 2 extension once a real caller needs it.
- **Migrating `exact.py`/`interval.py`/`certified.py`'s actual function BODIES into `idm/types.py`.**
  Phase 1 wraps; it does not move code. `solve.py`'s registry, its own tier bookkeeping,
  `_COQ_BACKED`, and dispatch loop are untouched.
- **Performance work** (interval arithmetic's well-known "wrapping effect" blowup over many chained
  ops, or GMP/flint-backed rationals instead of Python's `Fraction`) — Phase 1 is a type/contract
  layer over the EXISTING arithmetic backends; no backend swap.
- **New number-theoretic or root-isolation algorithms.** Every algorithm this pillar exposes already
  exists in the repo (§c); Phase 1 adds no new numeric method, only the typed/tiered surface.
